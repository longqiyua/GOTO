# 二、产品概览

### 核心交互基线

搜索框是软件唯一核心交互主体；快捷手势正式退出当前产品范围，仅保留作为搜索输入增强的快捷索引。统计默认未激活，未激活时全部指标为零；长按激活后，搜索、应用启动和快捷索引按真实事件实时记录，且不依赖统计页面是否可见。

### 背景与问题

现状：国内手机普及率长期且仍将稳定处于高位；手机应用生态持续发展，应用总数量持续攀升；桌面端有 Listary,Flow Launcher,Raycast 等应用搜索和启动的效率工具，手机除了原生搜索功能外相应缺乏

背景：

1. 手机系统原生的下拉/负一屏搜索承载了过多非核心业务，导致搜索结果冗余，速度偏慢，无法聚焦于"本地应用启动"的纯净体验
2. 原生搜索功能出于功能聚合的目的，往往只有简单的匹配功能，且深度与拓展度不足

<br>

### 产品介绍

GOTO 是一款专注于移动端本地应用快速搜索与启动的效率工具

<br>

### 产品定位

GOTO 区别于系统原生搜索，GOTO 聚焦本地应用启动场景，提供更快、更精准、更纯粹的搜索体验

<br>

### 产品目标

帮助用户快速定位并启动目标应用，降低应用启动过程中的时间成本与操作阻力，打造更高效、更纯粹的移动端应用启动体验

<br>

### 产品非目标

1. AI智能化
    - 原因：聚焦本地应用启动体验，优先保证轻量、快速、稳定，同时控制产品复杂度与开发成本。
2. 云同步
    - 原因：暂无多端协同需求，暂时没有多端开发计划，暂仅提供导入/导出多格式数据功能
3. 交流社区功能
    - 原因：社区并非核心使用场景，且已有成熟产品满足相关需求，引入社区会增加产品复杂度，偏离效率工具定位。
4. 用户全面自定义界面样式（CSS等）
    - 原因：当前版本优先统一UI/UX保证简洁易用，将开发资源集中于搜索效率与核心功能优化，自定义需求覆盖用户范围较小。
5. 插件拓展生态
    - 当前版本以核心功能稳定性和易用性为主，暂不开放扩展能力，避免增加不必要的维护和开发成本
6. 算法自定义
    - 移动端用户对极度的自定义需求较弱，且会大幅度增加软件维护成本和导致一些难以测试的稳定性问题，后续仅考虑作为桌面版功能之一

<br>

### 解决方案

1. 聚焦本地应用搜索，去除非核心信息干扰；
2. 支持模糊匹配、拼音匹配、缩写匹配等多种搜索方式
3. 基于用户使用习惯进行智能排序提供毫秒级搜索反馈，实现一步启动
4. 采用轻量化交互设计，减少用户操作路径

<br>

# 三、产品设计

### 需求分析

<br>

### 用户需求

1. 用户希望能够通过自然输入快速找到目标应用，即使存在拼写错误、输入不完整或使用习惯差异，也能获得准确的搜索结果
2. 用户希望搜索过程能够保持即时响应，同时避免输入过程中产生卡顿、延迟或无意义的频繁刷新
3. 用户希望首次使用时能够快速理解产品，并根据个人语言习惯完成基础配置
4. 用户希望通过更少的操作步骤快速启动高频应用，提高应用启动效率
5. 用户希望打开应用后能够直接看到符合当前使用场景的常用应用入口，减少重复搜索操作
6. 用户希望根据个人审美、环境和使用习惯调整产品界面，使工具更符合自己的使用方式
7. 用户希望无需准确记忆应用名称，也能通过表达使用目的或应用类型快速找到目标应用
8. 用户希望产品能够适应不同视觉需求，保证更多用户能够舒适、正常地使用应用
9. 用户希望了解自己的应用使用习惯，同时让系统根据个人行为优化应用推荐和排序效果
10. 用户希望能够自主控制个人数据，包括备份、迁移、恢复和删除，保障数据管理自由

<br>

### 功能需求

1. 系统需要提供快速应用搜索能力，支持多种输入方式和容错匹配，提高用户定位目标应用的效率
2. 系统需要根据用户输入行为动态调整搜索刷新机制，在保证实时反馈的同时降低无效计算和资源消耗
3. 系统需要提供完整的基础页面和设置功能，支持用户完成初始化配置以及基础使用操作
4. 系统需要提供快捷手势、快捷索引等快速访问方式，减少用户启动应用所需操作步骤
5. 系统需要提供首页应用展示入口，根据用户行为和自定义设置展示高频使用应用
6. 系统需要支持界面样式、主题模式、颜色以及显示方式调整，满足用户个性化使用需求
7. 系统需要支持基于应用分类和语义信息的搜索方式，使用户能够通过使用意图快速找到目标应用
8. 系统需要提供视觉辅助和色觉辅助功能，提升不同视觉条件下用户的使用体验
9. 系统需要记录用户应用使用行为，并通过统计数据辅助应用排序、推荐和使用分析
10. 系统需要提供用户数据导入、导出、重置和清理能力，保障用户对个人数据的控制权

<br>

### 非功能需求

1. 性能需求：需要快速响应能力，应用搜索等过程不能有肉眼可见延迟，保证核心操作迅速且流畅；同时，需要控制后台运行，避免过多占用内存和系统计算资源，保持软件的轻量化设计理念
2. 稳定性需求：具备稳定运行能力，在应用数量变化、数据异常或长时间使用情况下，仍能保持正常工作
3. 兼容性需求：系统应适配不同 Android 系统版本、设备性能和屏幕规格，保证不同设备下的使用体验
4. 隐私安全需求：用户应用列表、搜索记录和使用统计数据默认本地存储，保障数据安全，防止隐私泄露
5. 可用和易用需求：系统操作流程应保持简单直接好上手，无需多余学习成本即可完成软件核心功能的使用
6. 可维护性需求：需要高内聚低耦合的高度独立化模块化设计，方便后续功能扩展，问题修复等
7. 可拓展性需求：系统要为未来新增的搜索算法提供拓展空间，而无需大规模重构
8. 可读性需求：代码中应加入注释，保证代码可读性优良，便于后续拓展开发与维护
9. 无障碍需求：要符合无障碍设计原则，支持不同视觉需求用户正常使用产品
10. 数据可靠性需求：用户配置数据、统计数据和索引数据应具备可靠存储机制，避免异常情况下的数据丢失

<br>

### 功能详情

1. 基本搜索与模糊匹配引擎
    - 基本搜索
        - 说明：依赖字母前缀匹配应用
    - 模糊匹配引擎
        - 说明：通过多维度并行匹配算法，对用户输入与应用名称、拼音、英文、字符集合等信息进行相似度计算，并结合键盘距离、历史使用行为等因素进行智能排序，实现低成本、高容错的应用搜索体验
        - 实现：
            - 支持精确匹配、前缀匹配、包含匹配、拼音匹配、英文匹配、T9映射、乱序匹配等多个匹配维度
            - 各匹配结果通过权重计算生成综合评分

            - 根据历史启动频率和最近使用时间进行排序修正
            - 默认返回最高评分前30个结果

1. 自适应刷新
    - 自适应防抖T1
        - 说明：根据用户输入速度与退格行为动态调整搜索触发延迟，在保证响应速度的同时减少无效搜索请求
        - 实现：启发式自适应控制算法（Heuristic Adaptive Control）HAC：t1 = clamp(pmax x(1+E),Tavgx2, 400ms)
    - 自适应节流T2
        - 说明：根据用户平均输入速度与波动情况动态调整搜索触发间隔，平衡实时反馈与系统性能消耗
        - 实现：启发式自适应控制算法（Heuristic Adaptive Control）HACt2​=clamp(Tavg​+σ,30ms,Tavg​×1.5)
    - 用户手动测试与自动测试
        - 说明：手动测试：用户自行输入软件提供的目标句子，检测各项输入数据（如pmax:最快输入速度，Tavg:字符之间的平均输入速度等；E:用户输错几率（退格次数/总输入次数））；自动测试：在用户完成一次手动测试后显示开关，处于待开启状态，开启之后，依赖用户实际搜索操作，后台监测数据
        - 实现：
            - 取近五次有效（单次偏差超过50%直接忽视；如果是连续pmax变化的话，取三次平均值
            - 初始状态，没有满足五次有效时，统一采用200ms
            - 参数透明，支持用户任意自定义，支持恢复与查看测试数据

2. 基本页面与设置
    - 语言切换
        - 说明：切换中文/英文
    - 欢迎页面
        - 说明：展示问候语，让用户选择偏好语言（中文/英文），与语言切换配合

3. 快捷手势与快捷索引
    - 快捷手势
        - 说明：通过绑定手势与对应的应用，在全局或者软件内，依赖标准/快速模式直接跳转对应应用
        - 联动：手势启动的应用会被统计系统（§3.9）记录为启动次数，反向影响首页卡片（§3.4）排序与模拟智能（§3.6）权重
    - 快捷索引
        - 说明：通过绑定字符与对应的应用，在搜索框输入对应字符，可依赖标准/快速模式直接第一索引/跳转对应应用
        - 联动：①与搜索框（§3.1）直接集成，输入绑定字符后由搜索引擎优先处理；②标准模式下索引结果置顶行为与模糊匹配引擎的排序逻辑协同；③快速模式启动行为被统计系统记录
    - 快捷索引 UX
        - 创建流程固定为"输入符号 → 选择应用 → 选择快速/标准 → 保存"。不提供手动区分大小写开关：同一小写归一组只有一个写法时大小写兼容；存在多个大小写变体时自动精确消歧。点击已保存行进入编辑，行尾开关仅负责启停，删除只在编辑态出现。
        - 标准模式必须在搜索结果生成后把目标应用置顶；快速模式完整命中后直接启动目标。保存、编辑、删除后立即重算大小写策略并本地持久化。

4. 首页卡片
    - 最近卡片
        - 说明：获取系统时间，依赖统计功能-分时段应用启动次数，显示当前时段的最常使用的前四个应用，以及临近一个时段的最常使用的第一个应用，一行三个，共两行
        - 联动：①与统计系统（§3.9）的"分时段应用启动次数"直接数据依赖；②与光感模式（§3.5）共用六时段划分逻辑，时段切换时卡片内容自动刷新；③与智能提示卡片（§3.7）的"即将打开的 2 个应用提示"形成"历史回顾 + 未来预测"的互补关系
    - 常用卡片
        - 说明：依赖统计功能-全时段应用启动次数，显示最常使用的前六个应用，一行三个，共两行
        - 联动：①与统计系统（§3.9）的"全时段应用启动次数"直接数据依赖；②与模拟智能（§3.6）的权重层（`getRuleWeights`）共享长期使用偏好数据
    - 自定义卡片
        - 说明：自定义添加应用，一行三个，最多支持4行共12个
        - 联动：自定义数据独立于统计系统，但点击启动行为仍会被统计系统记录，反向影响最近卡片和常用卡片的排序

5. 个性化
    - UI风格切换
        - 说明：切换扁平/拟态风格
    - 深浅模式切换
        - 说明：切换背景颜色与字体颜色
    - 自定义强调色
        - 说明：自定义填写色值/随机生成颜色/使用预设黑/白/砖红（默认）强调色
    - 时钟详情/12/24小时制
        - 说明：切换是否显示秒钟以及切换12/24小时制
    - 光感模式
        - 说明：根据用户所在地理位置、时间或自定义时区动态调整界面色温，降低长时间使用造成的视觉疲劳
        - 联动：①与 Micro-Context（§3.13）的"地点/光感模式"维度联动，光感模式启用时该维度 boost 激活（导航 +30、音乐 +15）；②与智能提示卡片（§3.7）的分时段问候语共用同一套六时段划分逻辑；③与首页卡片（§3.4）的最近卡片共用时段数据；④与统计系统（§3.9）的 24 小时活跃度共用小时判定
        - 设计系统（v1.6 定档，陶瓷质感 Ceramic Texture）：
            - **材质定义**：光感模式全局弃用传统毛玻璃（`backdrop-filter: blur`），统一采用"陶瓷质感"——通过 135° 渐变背景、精细内阴影（顶部 1px 高光 `rgba(255,255,255,0.45) inset` + 底部 1px 暗影 `rgba(0,0,0,0.03) inset`）、极轻外投影（`0 4px 14px rgba(12,14,20,0.05)`）模拟温润釉面效果，避免塑料感与液态玻璃的过度反光
            - **样式隔离**：通过 `.light-sense` 类前缀结合 `light-sense-light` / `light-sense-dark` 双变体实现状态隔离；光感模式样式始终在标准模式基础上叠加修改（`body.light-sense.light-sense-dark` 等），而非独立重写，保证几何结构一致性
            - **统一覆盖范围**：`.search-card`、`.slot-card`、`.section-card`、`.sub-card`、`.result-row`、`.sc-ready-hint` 等核心组件统一应用陶瓷质感规则，使用 `color-mix(in srgb, var(--ink) 6%, transparent)` 实现半透明边框
            - **搜索框规范**：光感模式下搜索框采用陶瓷/玉石质感，去除突兀白边（边框使用 `color-mix(in srgb, var(--ink) 6%, transparent)` 而非 `var(--line-strong)`），继承标准模式 `padding:0` 保证左右边界对齐
            - **返回按钮全局通用**：设置二级页面左上角返回按钮在标准模式与光感模式下样式完全统一，采用线条外框风格（`.bp-icon-arrow` 使用 `inline-flex` 垂直居中，SVG 通过 CSS 控制 `width:13px;height:13px` 而非硬编码属性）
        - 时间过渡算法（v1.6 优化，均匀化处理）：
            - **核心变量**：`--daylight-intensity` 基于色温亮度动态计算，作为光感模式颜色过渡的全局驱动变量
            - **关键帧优化**：`LIGHT_SENSE_COLOR_KEYFRAMES` 关键帧针对 18:00（日落）和 13:30（午后）附近的颜色过渡进行均匀化处理，调整 RGB 值和 warmth 参数，配合 `cubic-bezier` 缓动函数消除突变跳变
            - **六时段映射**：清晨 05–08 / 上午 08–12 / 中午 12–14 / 下午 14–18 / 晚上 18–24 / 凌晨 00–05，与智能提示卡片分时段问候语、首页最近卡片时段判定完全一致
            - **过渡约束**：任意相邻时段的颜色变化必须满足视觉连续性，禁止出现肉眼可感知的跳变；过渡曲线采用平滑的 `cubic-bezier(0.4, 0, 0.2, 1)` 缓动

12. 增强模拟智能（v1.5，Enhanced Simulated Intelligence）
    - 功能：在基础模拟智能之上，增强模式引入六项能力：欧氏距离优化、多维度并行搜索、模式频率统计、搜索周期记录、快速渲染路径、犹豫补偿延迟。仅在用户同时开启"模拟智能"和"增强模拟智能"时生效。
    - 设计：
        - 开关存储：`goto_simint_enabled`（基础）+ `goto_enhanced_simint`（增强）
        - UI 层：增强开关作为基础开关的延展菜单，标注 "Lindo Lab" 品牌标识
        - 多端同步：Web 端 `isEnhancedSimIntEnabled()` 检测；Kotlin 端 `SharedPreferences` 对应键
    - 算法：
        1. **欧氏距离优化**：QWERTY 键盘行偏移补偿 `[0, 0.5, 1.25]` + 对角线惩罚 0.15
        2. **多维度并行搜索**：各模糊匹配模式独立计算后取并集，避免单一模式主导
        3. **模式频率统计**：`modeFrequency` 记录每次搜索贡献最大的模式，多周期统计后提高高频模式权重
        4. **搜索周期记录**：`cycleTimestamps` 记录"搜索→启动"时间戳，短时间快速启动标记为误操作
        5. **快速渲染路径**：输入间隔 < 50ms 且高度匹配时跳过自适应刷新
        6. **犹豫补偿延迟**：高斯按键距离衰减或邻位交换纠错触发时，叠加 Δ_hesitate 到防抖公式
    - 边界：
        | 边界场景 | 处理方式 |
        | --- | --- |
        | 增强开关关闭但基础开关开启 | 仅基础模拟智能生效，Micro-Context 不启用 |
        | 搜索周期 < 500ms（误操作） | 不写入模式频率统计，不更新权重 |
        | 输入间隔极端值（< 10ms） | 快速渲染路径仍需通过 `_isHighConfidenceMatch` 置信度检测 |
        | `modeFrequency` 数据为空 | 回退到默认等权模式 |
        | localStorage 写入失败 | 所有统计静默降级，不影响搜索主流程 |

13. 微观上下文（v1.5，Micro-Context）
    - 功能：联合六个维度（设备信息、地点/光感模式、时间、手机使用情况、用户统计、剪贴板识别）计算推荐权重，仅在增强模拟智能下启用。Web 端自动注入 Mock 数据，Kotlin 端映射真实系统权限。
    - 设计：
        - 存储键：`goto_engine_micro_context`
        - 自动 Mock：`autoMockMicroContext()` 在每次 `fuzzySearch` 调用时自动刷新（增强模式启用时）
        - 无 UI 权限开关：Web 端无需用户手动授权；Kotlin 端通过系统权限弹窗获取
    - 算法：
        ```mermaid
        flowchart LR
            A[设备信息] --> G[联合推荐权重]
            B[地点/光感模式] --> G
            C[时间] --> G
            D[手机使用情况] --> G
            E[用户统计] --> G
            F[剪贴板识别] --> G
            G --> H[搜索结果重排]
        ```
        权重计算（`_getMicroContextBoost`）：
        - 设备信息：低端设备（SDK<24）压制重型应用 -20
        - 地点：光感模式下导航 +30、音乐 +15
        - 时间：深夜推荐时钟/睡眠 +35，早高峰推荐新闻/地图 +25
        - 手机使用情况：屏幕亮屏 >120min 推荐娱乐 +25，切换 >8次 推荐效率 +20
        - 用户统计：历史选择 ≥3 次的应用 +8/次（上限 +30）
        - 剪贴板：快递单号→物流 +40，URL→浏览器 +35，电话→通讯录 +30
    - 边界：
        | 边界场景 | 处理方式 |
        | --- | --- |
        | 某维度数据缺失（granted=false） | 该维度 boost=0，不影响其他维度 |
        | 剪贴板为空 | detectedType='text'，不产生 boost |
        | 光感模式未启用 | location.mode='normal'，仅基础地点权重 |
        | Mock 数据刷新间隔 < 60s | 跳过本次刷新，使用缓存 |
        | 权限被拒绝（Kotlin 端） | 对应维度 granted=false，降级运行 |
        | Boost 总和过大 | 单应用总 boost 上限 80，避免压制正常匹配分 |

    - 功能：在 24 小时分时段排名（严格按小时分段）下方新增卡片，基于 GOTO 使用间隔动态聚类时段，展示每个时段的 Top 5 应用排名。
    - 设计：
        - 卡片位置：统计页面，24 小时分时段排名卡片下方
        - 独立运行：与其他统计卡片共同展示，互不影响
        - 数据展示：时段区间（如 13:02–18:02）、总启动次数、持续时长、Top 5 应用
    - 算法：
        1. **切分点提取**：仅以 GOTO 启动事件为时间点
        2. **最小间隔过滤**：相邻 GOTO 启动间隔 < 5 分钟视为同一时段内连续操作
        3. **最大间隔截断**：相邻切分点间隔 > 6 小时跳过该时段
        4. **时段构建**：相邻切分点形成时段，区间可重叠（边界点同时属于前后时段）
        5. **应用排名**：时段内所有应用启动（含非 GOTO 启动）按次数降序取 Top 5
        6. **多时段出现**：同一应用可在多个时段的 Top 5 中重复出现
        ```mermaid
        flowchart TD
            A[GOTO 启动事件序列] --> B{相邻间隔}
            B -->|< 5min| C[合并到当前时段]
            B -->|5min ~ 6h| D[形成新时段]
            B -->|> 6h| E[跳过，不形成时段]
            D --> F[收集时段内所有启动事件]
            F --> G[按应用计数排序]
            G --> H[取 Top 5]
            H --> I[渲染时段卡片]
        ```
    - 边界：
        | 边界场景 | 处理方式 |
        | --- | --- |
        | GOTO 启动事件 < 2 次 | 不生成任何时段，卡片显示空状态 |
        | 时段内无应用启动 | 跳过该时段 |
        | 时段跨天（如 23:00–02:00） | 按实际时间戳计算，日期标签附加到时段标题 |
        | 应用名称为空或异常 | 过滤该事件，不参与排名 |
        | 时段数量 > 20 | 仅展示最近 20 个时段 |
        | Top 5 中有并列 | 按应用名 localeCompare 排序 |

### 补充解释

GOTO 的核心理念是在保持轻量、快速、隐私优先的基础上，逐步从传统应用启动工具演进为本地智能行动路由系统。除基础搜索与模糊匹配能力外，GOTO 通过模拟智能与元标签索引技术，对应用本身进行能力抽象，将应用名称、功能类别、使用场景、用户行为等信息建立关联，使用户无需准确记忆应用名称，也可以通过自然语言表达目标需求完成应用定位。例如用户输入"聊天""导航""听歌"等意图时，系统能够根据标签索引和历史行为推荐对应应用。在智能排序方面，GOTO 引入基于时间维度的行为统计机制，包括 24 小时活跃度分析、分时段应用启动次数以及全时段使用频率统计，使推荐结果能够同时结合长期习惯与当前时间场景。进一步通过上下文感知路由（Chain-of-Action Routing）捕获用户前序行为状态，根据当前任务链预测下一步可能需求，例如浏览商品后自动关联物流查询，游戏后优先推荐社交工具。同时，GOTO 通过本地行为反馈机制持续优化推荐结果。系统根据用户点击、忽略、主动调整等行为动态修正权重，并支持用户手动纠正错误推荐，使规则能够不断适应个人习惯。结合智能提示卡片，GOTO 可以在合适场景主动提供下一步建议，实现从"用户寻找应用"到"系统辅助行动"的转变。所有智能能力均**基于本地数据**处理，不依赖云端服务，保证低延迟、高可靠和隐私安全。未来 GOTO 将持续探索确定性智能与个人行为模型结合，让移动设备具备更加自然、高效且可控的交互体验。

# 四、交互设计

### P0 交互原则

1. 搜索框是首页唯一功能主体；默认位于可用屏幕中心，首次点击以有阻尼的自然动画上移，宽度不得跳变。
2. 智能提醒始终与搜索框组成同一组件；搜索结果容器按实际结果数量伸展，不固定拉满屏幕。
3. 所有强调色背景使用亮度计算后的动态反色，标准、质态、光感模式、浅色和深色共享同一规则。旧内部值 `flat/neumorphic` 仅为兼容存储，不再作为界面文案。
4. 设置页坚持少即是多。进阶功能卡只有一个开关，禁止点击母卡片展开；详细解释统一进入右侧文档。
5. 二级页返回区遵循安全区，同时与首张内容卡保持紧凑的视觉关联。

### 设计规范

动效

1. 全局禁止使用突兀弹窗，采用卡片变形，延展，拉伸等生产方式来呈现二级内容
2. 保证动画微阻尼感与弹性，提供渐变式的呼吸感动画

配色：全局采用黑白灰三色作为基本色，并保持唯一强调色及其渐变色系，且强调色仅用于按钮标识，视觉引导等；不接受五颜六色

字体：中文采用思源黑体，英文采用Nunito字体，特殊数字采用Jetbrain Mono字体,部分字体采用Geist字体；总体字体偏粗，避免过细和太粗

圆角：全局统一圆角尺寸12px；拒绝纯圆或直角等硬几何风格

材质：提供扁平与拟态两种视觉风格。拟态模式采用高透明度的模糊材质，通过柔和光影和细腻纹理模拟陶瓷、玉石等自然材质质感，避免液态玻璃风格带来的过度反光与装饰感。

### 开发说明

约束：

1. 应用数据来源于 Android PackageManager
2. 搜索索引首次启动时建立，后续监听应用安装、卸载事件自动更新
3. 排序依据历史使用频率及最近使用时间综合计算
4. 所有数据默认本地存储，不上传任何用户数据
5. 搜索索引首次启动时建立，后续监听应用安装、卸载事件自动更新

8. 等等

### 实现方式

技术栈：Kotlin + Android SDK 34 + ViewBinding + Coroutines + SQLite

架构模式 ：MVVM(View（视图）+ViewModel（逻辑）+Model（数据结构）) + Repository(软件数据) + Service（系统服务）

总览：采用 Kotlin + Android SDK 34 开发，整体遵循 MVVM 架构。应用启动时通过 AppIndexEngine 扫描系统应用建立索引，用户输入时由 SearchService 统一调度搜索流程，支持精确匹配和模糊匹配引擎，搜索结果通过 Coroutines Flow 实时推送到 UI。核心功能包括：桌面快捷搜索入口（已规划去除，转为智能提示卡片）、手势录制与识别、快捷字符绑定、高频应用统计。数据层使用 SQLite 持久化用户配置和使用记录，通过 DAO 模式进行数据访问。搜索性能通过缓存策略（64条上限、5分钟TTL）和自适应刷新机制（基于打字速度动态调整搜索时机）保障响应速度。

#### 优化原则（用于后续新增代码评审）

1. **单一职责**：每个类/函数只做一件事；ViewModel 拆分不超过 3 个包依赖。
2. **包名与目录一致**：禁止 `AdaptiveRefresh/TypingSpeedTracker.kt` 这种目录与 package 不一致的情况。
3. **枚举单点定义**：同一概念禁止多处重复定义；如需不同视图，使用扩展函数或映射。
4. **废弃即标注**：使用 `@Deprecated` 注解（Kotlin）或注释（JS）明确替代方案与移除时间。
5. **接口优先**：跨模块调用优先通过 interface 解耦，便于后续替换实现。
6. **存储层抽象**：所有 localStorage / SharedPreferences / SQLite 访问必须通过 DAO 层，禁止 UI 层直接调用。
7. **双端一致性**：Kotlin 与 JS 同名算法需保证匹配维度、评分权重、返回结构一致，新增测试用例同步覆盖。
