## 产品概览
### 背景与问题
现状：国内手机普及率长期且仍将稳定处于高位；手机应用生态持续发展，应用总数量持续攀升；桌面端有Listary,Flow Launcher,Raycast等应用搜索和启动的效率工具，手机除了原生搜索功能外相应缺乏
#### 背景：
手机系统原生的下拉/负一屏搜索承载了过多非核心业务，导致搜索结果冗余，速度偏慢，无法聚焦于“本地应用启动“的纯净体验
原生搜索功能出于功能聚合的目的，往往只有简单的匹配功能，且深度与拓展度不足

### 产品介绍
GOTO 是一款专注于移动端本地应用快速搜索与启动的效率工具

### 产品定位
GOTO 区别于系统原生搜索，GOTO 聚焦本地应用启动场景，提供更快、更精准、更纯粹的搜索体验

### 产品目标
帮助用户快速定位并启动目标应用，降低应用启动过程中的时间成本与操作阻力

### 产品非目标
AI智能化
原因：聚焦本地应用启动体验，优先保证轻量、快速、稳定，同时控制产品复杂度与开发成本。
补充边界：本条不否定已经存在的本地、可解释规则能力。GOTO Prethink、元标签索引和模拟智能属于确定性本地模块，不依赖云端大模型；未来模型只作为隐藏的预处理接入点，不能改写原始查询或绕过 Engine 的最终解释权。
云同步
原因：暂无多端协同需求，暂时没有多端开发计划，暂仅提供导入/导出多格式数据功能
交流社区功能
原因：社区并非核心使用场景，且已有成熟产品满足相关需求，引入社区会增加产品复杂度，偏离效率工具定位。
用户全面自定义界面样式（CSS等）
原因：当前版本优先统一UI/UX保证简洁易用，将开发资源集中于搜索效率与核心功能优化，自定义需求覆盖用户范围较小。
插件拓展生态
当前版本以核心功能稳定性和易用性为主，暂不开放扩展能力，避免增加不必要的维护和开发成本
算法自定义
移动端用户对极度的自定义需求较弱，且会大幅度增加软件维护成本和导致一些难以测试的稳定性问题，后续仅考虑作为桌面版功能之一

### 解决方案
聚焦本地应用搜索，去除非核心信息干扰；
支持模糊匹配、拼音匹配、缩写匹配等多种搜索方式
基于用户使用习惯进行智能排序提供毫秒级搜索反馈，实现一步启动
采用轻量化交互设计，减少用户操作路径

## 产品设计
### 用户需求
用户希望能够通过自然输入快速找到目标应用，即使存在拼写错误、输入不完整或使用习惯差异，也能获得准确的搜索结果
用户希望搜索过程能够保持即时响应，同时避免输入过程中产生卡顿、延迟或无意义的频繁刷新
用户希望首次使用时能够快速理解产品，并根据个人语言习惯完成基础配置
用户希望通过更少的操作步骤快速启动高频应用，提高应用启动效率
用户希望打开应用后能够直接看到符合当前使用场景的常用应用入口，减少重复搜索操作
用户希望根据个人审美、环境和使用习惯调整产品界面，使工具更符合自己的使用方式
用户希望无需准确记忆应用名称，也能通过表达使用目的或应用类型快速找到目标应用
用户希望产品能够适应不同视觉需求，保证更多用户能够舒适、正常地使用应用
用户希望了解自己的应用使用习惯，同时让系统根据个人行为优化应用推荐和排序效果
用户希望能够自主控制个人数据，包括备份、迁移、恢复和删除，保障数据管理自由

### 功能需求
系统需要提供快速应用搜索能力，支持多种输入方式和容错匹配，提高用户定位目标应用的效率
系统需要根据用户输入行为动态调整搜索刷新机制，在保证实时反馈的同时降低无效计算和资源消耗
系统需要提供完整的基础页面和设置功能，支持用户完成初始化配置以及基础使用操作
系统需要提供快捷手势、快捷索引等快速访问方式，减少用户启动应用所需操作步骤
系统需要提供首页应用展示入口，根据用户行为和自定义设置展示高频使用应用
系统需要支持界面样式、主题模式、颜色以及显示方式调整，满足用户个性化使用需求
系统需要支持基于应用分类和语义信息的搜索方式，使用户能够通过使用意图快速找到目标应用
系统需要提供视觉辅助和色觉辅助功能，提升不同视觉条件下用户的使用体验
系统需要记录用户应用使用行为，并通过统计数据辅助应用排序、推荐和使用分析
系统需要提供用户数据导入、导出、重置和清理能力，保障用户对个人数据的控制权
系统需要在正式搜索前提供独立的 GOTO Prethink 预联想，为 Engine 提供有限、可解释且不改变原始输入的平行查询候选
系统需要通过 GOTO Where 将时间、行为链与应用候选转换为可关闭的智能提醒，并在 Android 宿主中支持真实系统通知
系统需要通过 SuperGOTO 统一承载进阶能力，同时保证基本搜索、GOTO Engine、GOTO Base 与 GOTO Where 的职责边界清晰
系统需要支持真实应用图标、应用色浅色系卡片和无图标灰色占位；Page 无法读取宿主图标时必须显示统一 `NULL` 占位，不伪造品牌图标

### 非功能需求
性能需求：需要快速响应能力，应用搜索等过程不能有肉眼可见延迟，保证核心操作迅速且流畅；同时，需要控制后台运行，避免过多占用内存和系统计算资源，保持软件的轻量化设计理念
稳定性需求：具备稳定运行能力，在应用数量变化、数据异常或长时间使用情况下，仍能保持正常工作
兼容性需求：系统应适配不同 Android 系统版本、设备性能和屏幕规格，保证不同设备下的使用体验
隐私安全需求：用户应用列表、搜索记录和使用统计数据默认本地存储，保障数据安全，防止隐私泄露
可用和易用需求：系统操作流程应保持简单直接好上手，无需多余学习成本即可完成软件核心功能的使用
可维护性需求：需要高内聚低耦合的高度独立化模块化设计，方便后续功能扩展，问题修复等
可拓展性需求：系统要为未来新增的搜索算法提供拓展空间，而无需大规模重构
可读性需求：代码中应加入注释，保证代码可读性优良，便于后续拓展开发与维护
无障碍需求：要符合无障碍设计原则，支持不同视觉需求用户正常使用产品
数据可靠性需求：用户配置数据、统计数据和索引数据应具备可靠存储机制，避免异常情况下的数据丢失
系统联动需求：Page 的文档正文、目录状态和左侧手机预览应保持同步；文档源更新后可重新生成静态 bundle，不需要修改页面逻辑
部署需求：`GOTO Page` 应可作为独立静态目录挂载到 GitHub Pages；页面在无 Android 宿主权限时仍可完成文档阅读和交互预览，但不得把预览行为误报为真实系统启动
设备适配需求：应覆盖窄屏、异形屏、平板、折叠屏和横竖屏变化；手机状态栏、搜索框延展、底部版本号和卡片网格不得发生遮挡或溢出

#### 基本设置
#### 语言切换
说明：切换中文/英文
#### 欢迎页面
说明：展示问候语，用户选择偏好语言（中文/英文）
#### 基本搜索与模糊匹配引擎
#### 基本搜索
说明：依赖字母前缀匹配应用
#### 模糊匹配
说明：通过多维度并行匹配算法，对用户输入与应用名称、拼音、英文、字符集合等信息进行相似度计算，并结合键盘距离、历史使用行为等因素进行智能排序，实现低成本、高容错的应用搜索体验
实现：
支持精确匹配、前缀匹配、包含匹配、拼音匹配、英文匹配、T9映射、乱序匹配等多个匹配维度
各匹配结果通过权重计算生成综合评分
根据历史启动频率和最近使用时间进行排序修正
默认返回最高评分前30个结果
#### GOTO Prethink 预处理
说明：Prethink 是独立于 Engine、Base、Where 的预联想层。它不修改用户输入，也不替代最终匹配，而是在正式搜索前猜测用户可能想输入的查询，并把带置信度的候选交给同一个 Engine 统一竞争。
实现：结合键盘邻位、字符交换、重复字符、缺失字符、拼音与英文转换、用户历史和当前已安装应用集合生成候选；每个候选携带 `query`、`confidence`、`source`、`editCost` 与 `explanation`。
约束：原始查询永远保留且权重最高；最多生成3–5个候选；低于最低置信度的候选直接丢弃；同一应用被多条路径召回时只取最高路径得分，并限制多路径奖励，避免结果分数膨胀。Prethink 可以作为 JS、Rust、Kotlin 的独立 API 入口，后续为模型接入预留接口。
#### 自适应刷新
#### 自适应防抖T1
说明：根据用户输入速度与退格行为动态调整搜索触发延迟，在保证响应速度的同时减少无效搜索请求
实现：启发式自适应控制算法（Heuristic Adaptive Control）HAC：t1 = clamp(pmax x(1+E),Tavgx2, 400ms)
#### 自适应节流T2
说明：根据用户平均输入速度与波动情况动态调整搜索触发间隔，平衡实时反馈与系统性能消耗
实现：启发式自适应控制算法（Heuristic Adaptive Control）HACt2​=clamp(Tavg​+σ,30ms,Tavg​×1.5)
#### 用户自动测试
说明：用户字符以索引软件，系统检测各项输入数据（如pmax:最快输入速度，Tavg:字符之间的平均输入速度等；E:用户输错几率（退格次数/总输入次数））；自动测试：
实现：
取近五次有效（单次偏差超过50%直接忽视；如果是连续pmax变化的话，取三次平均值
初始状态，没有满足五次有效时，统一采用200ms
参数透明，支持用户任意自定义，支持恢复与查看测试数据

### 补充解释
GOTO 的核心理念是在保持轻量、快速、隐私优先的基础上，逐步从传统应用启动工具演进为本地智能行动路由系统。除基础搜索与模糊匹配能力外，GOTO 通过模拟智能与元标签索引技术，对应用本身进行能力抽象，将应用名称、功能类别、使用场景、用户行为等信息建立关联，使用户无需准确记忆应用名称，也可以通过自然语言表达目标需求完成应用定位。例如用户输入“聊天”“导航”“听歌”等意图时，系统能够根据标签索引和历史行为推荐对应应用。在智能排序方面，GOTO 引入基于时间维度的行为统计机制，包括 24 小时活跃度分析、分时段应用启动次数以及全时段使用频率统计，使推荐结果能够同时结合长期习惯与当前时间场景。进一步通过上下文感知路由（Chain-of-Action Routing）捕获用户前序行为状态，根据当前任务链预测下一步可能需求，例如浏览商品后自动关联物流查询，游戏后优先推荐社交工具。同时，GOTO 通过本地行为反馈机制持续优化推荐结果。系统根据用户点击、忽略、主动调整等行为动态修正权重，并支持用户手动纠正错误推荐，使规则能够不断适应个人习惯。结合智能悬浮窗与行动卡片，GOTO 可以在合适场景主动提供下一步建议，实现从“用户寻找应用”到“系统辅助行动”的转变。所有智能能力均基于本地数据处理，不依赖云端服务，保证低延迟、高可靠和隐私安全。未来 GOTO 将持续探索确定性智能与个人行为模型结合，让移动设备具备更加自然、高效且可控的交互体验。

### 开发说明
### 约束：
应用数据来源于 Android PackageManager
搜索索引首次启动时建立，后续监听应用安装、卸载事件自动更新
排序依据历史使用频率及最近使用时间综合计算
所有数据默认本地存储，不上传任何用户数据
搜索索引首次启动时建立，后续监听应用安装、卸载事件自动更新
搜索结果默认限制30条，缓存最多64条且5分钟后失效
单次的搜索输入字符数超过50时，提示"输入内容过长，请精简后重试
等等

### 实现方式
技术栈：Kotlin + Android SDK 34 + ViewBinding + Coroutines + SQLite
架构模式 ：MVVM(View（视图）+ViewModel（逻辑）+Model（数据结构）) + Repository(软件数据) + Service（系统服务）
总览：采用 Kotlin + Android SDK 34 开发，整体遵循 MVVM 架构。应用启动时通过 AppIndexEngine 扫描系统应用建立索引，用户输入时由 SearchService 统一调度搜索流程，支持精确匹配和模糊匹配引擎，搜索结果通过 Coroutines Flow 实时推送到 UI。核心功能包括：悬浮窗搜索服务、手势录制与识别、快捷字符绑定、高频应用统计。数据层使用 SQLite 持久化用户配置和使用记录，通过 DAO 模式进行数据访问。会员体系通过 LicenseManager 验证授权，控制高级功能的使用权限。搜索性能通过缓存策略（64条上限、5分钟TTL）和自适应刷新机制（基于打字速度动态调整搜索时机）保障响应速度。

## Page 源与代码实现补充

本节只补充当前实现与原始 PRD 的对应关系，不改变上文产品结构和需求含义。

| PRD 能力 | Page 源实现 | Android / 数据边界 |
| --- | --- | --- |
| 基本搜索与模糊匹配 | `GOTO Page/index.html` 的搜索状态、结果卡片与空结果状态；页面只负责输入、展示和联动 | GOTO Engine 负责最终匹配；Kotlin 宿主提供已安装应用清单 |
| GOTO Prethink 预处理 | `prethink/goto-prethink.js` 生成带置信度、来源和解释的并行候选，原始查询始终保留 | JS、Rust、Kotlin 共享候选 DTO；不修改 Engine、Base、Where |
| 首页最近 / 常用卡片 | Page 读取真实统计快照，按当前时段与全时段排序，并在样本不足时使用已有数据兜底 | GOTO Base 保存应用事实和行为事件；不生成演示数据 |
| 统计系统 | `stats` 面板展示搜索、启动、输入字符与应用排名 | 只有从 GOTO 发起的真实启动进入统计 |
| 光感模式 | Page 根据权限、时区和预览时刻切换陶瓷/玉石材质与亮面方向 | Android 系统权限与位置能力由 Kotlin 宿主负责 |
| 文档与手机联动 | `loadDocTo()` 加载当前文档，`DOC_PREVIEW_ACTIONS` 将文档动作映射到手机真实卡片 | WebView 继续使用既有 Bridge，不改变字段语义 |
| 文档离线发布 | `GOTO Page/Document/` 是文档源，`document-bundle.js` 是静态托管回退 | Android asset 从 Page 源同步生成 |

手机预览只作为当前功能的可视化基线；本次更新仅替换 PRD 文档内容，不修改手机端功能、搜索引擎、Base 数据契约或 Where 提醒逻辑。
